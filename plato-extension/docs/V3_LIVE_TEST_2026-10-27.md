## Bug found and fixed: typing over what the page filled from the resume

Lever fills name, email, phone, location, company and links from the uploaded resume 3–6 s after the upload. The model's turn (planned from a read taken before the upload) then clicked those fields and typed, and `type` appends: "Test SeekerTest Seeker", doubled email and phone. The model noticed on its next read and repaired with form_input, so the final values were right, but it cost a turn and looked wrong on screen.

Fix (generic, no site rule), in `v3-reader.ts` + `executor.ts`:
- the reader remembers each text field's value as the model last read it (`describe`); `changed` lists the fields whose value the page set since, and the active ref;
- `type` into such a field is refused: `Refused: "Full name" already holds "Test Seeker", filled by the page after your last read. Typing would append to it. Read the page again; to replace a value use form_input.` The rest of that turn is not run (existing rule), the model reads and continues;
- `file_upload` waits up to ~6 s for the parse and reports: `Uploaded Test_Seeker_CV.pdf. The page then filled from it: Full name = "Test Seeker"; Email = …`;
- `typed` (after type/key) and form_input mark a value as ours, so a second type into a type-ahead (", Egypt" after "Cairo") is not refused.

Live after the fix (Lever run 2): upload result listed the filled fields, the one type into "Full name" was refused, the model re-read and only typed the two textareas. 5 turns instead of 8, $0.06 instead of $0.13.

Specs: `test/v3-reader.spec.ts` (changed/typed), `test/v3-executor.spec.ts` (refused type, type elsewhere, upload report).

## Real Submit, 13:36 (owner's go for the Lever item)

"Submit for me" on the armed Lever item. Two things happened:

1. **First press did nothing** (13:23). The `--submit=off` flag had replaced `true` in the `auto` expression, so production builds ignored the "Submit for me" override. Fixed: the override wins whatever the flag (`panel/main.ts`, both `auto` lines). Browser relaunched on the rebuilt bundle (item fell to "Please check / page_closed", settled, re-batched, re-run: SUBMIT_READY in 35 s, 5 turns).
2. **Second press reloaded the page and refilled the whole form**, then pressed SUBMIT APPLICATION. Lever answered with an hCaptcha challenge; the brain read the page and stopped: `Stopped for the seeker: The site asks for a human check (captcha)`. Panel: "Needs you", with Try again. The form is still on the page, hCaptcha token empty, URL still `/apply`: **the application was not sent.** The person must press Submit in that window and solve the challenge.

The refill happened because "Submit for me" re-entered the loop with `event: start`, and the backend opens a **new** conversation on every `start` (`v3-session.service.ts` turn(): `if (req.event === 'start' || !s) s = open(...)`), so the brain is told "Apply to this job: URL" and navigates. The "Start again from the page as it is now: read it, keep what is filled" prompt on the same line is dead code. Extension-side fix (no backend change): an armed item (`AWAITING_SUBMIT`) plus allowed Submit resumes with `event: submit`, continuing the same conversation; `session_lost` still falls back to `start`. `run.ts` counts a run that begins at Submit as the one press. Spec added in `test/v3-run.spec.ts`. Not exercised live after the fix (the only authorized live Submit was this Lever one).

Cost of the item today: 2 runs, 13 turns (the second run's refill included). Day total across the four items: $1.11.

## Findings added after the Submit pass

- F6 Backend `start` always opens a new session: the "keep what is filled" branch never runs. Worth fixing server-side too (keep the session when it has no pending tool calls), so a panel "Try again" after a crash does not refill.
- F7 After a captcha that appears **on** Submit (Lever's hCaptcha), `submitPressed` stays true on the server. If the site does not auto-submit after the challenge, the brain's next press is refused by the one-Submit gate and the item ends "unconfirmed". The seeker's own press is the way through today; the panel says so.
- F8 The chat answered the captcha notice on its own ("There are no jobs currently blocked. All applications are either filled or awaiting your action…"): the stop notice seems to be fed to the chat model as a seeker message. Cosmetic, but misleading.

## Findings not fixed

- F1 Per-row "Start" starts the whole waiting queue (the run loop drains it, 4 at a time) while the header says "Applying to 1 job". Either the header or the behaviour is wrong.
- F2 Greenhouse cost: 20 turns, $0.73, 523k input tokens, cache 37%. Most turns were screenshot + coordinate clicks on react-select lists; the "US state" combobox took three attempts ("I am not" typed three times). Worth a prompt/tool nudge towards `find` + ref clicks on option lists before Phase 4's cost work.
