# How the extension applies on a page (generic, not per-site)

The same loop on every site (`panel/ai-apply.ts`, driven by `panel/main.ts` `runAi`). The site's name never matters: a listing with an Apply button, a one-shot form, a five-step dialog and a confirmation page are all just pages.

1. **Settle.** A page is looked at until two looks 800 ms apart agree and `document.readyState` is complete (`dom/snapshot.ts`, `loading`). Nothing is decided on a half-rendered page.
2. **Inspect (no AI).** `dom/inspect.ts` lists every control a person could see and edit, through open shadow roots: text/email/tel/number/date/url, selects, radio groups, tick lists, type-ahead inputs, uploads. Sensitive fields are counted and never described. One plausible form is reviewed; otherwise the whole page, each field tagged with its form's label. `dom/snapshot.ts` adds the page's text, open dialog, pressable controls (label + a temporary `eN` ref) and alerts. Never field values.
3. **One AI decision per page** (`POST /extension/v1/items/:id/decide`, `apply/page-decide.agent.ts`): page type, a value for every field it can support from the seeker's whole profile, the required fields it cannot answer and why, the ONE next move (`press` a ref with intent open_apply / next / review / submit / other, `wait`, `ask`, `skip`, `done`), and at most one question only the seeker can answer (a required skill the profile does not show). `finishDecision` re-checks everything: values through the typed gate, unfilled required fields counted, the move through `apply/page-plan.guard.ts` (a ref that is not on the page, a submit without opt-in or with gaps, a press that already did nothing twice).
4. **Fill and verify** (`dom/fill.ts`). One round per decision; every value is read back. A tick list ends up with exactly the listed options; a type-ahead is typed, then the matching option is clicked and the pick remembered. Fields the page reveals while filling (a city after the country) get their own decision before any move. A value that did not stick goes back to the AI once or twice with why (the repair call) and only then to the seeker.
5. **Resume.** An upload field asks once per application which resume to use (profile, or one built for this job by the resume engine); the answer lives on the application. Consent boxes are only ever ticked by the seeker.
6. **Move, then inspect the new page.** The named control is found again by its label just before pressing. Submit is pressed at most once; `done` counts only if the page itself shows a confirmation; with auto-submit off the job is armed and the seeker presses Submit. Nothing is decided again while the page has not changed. Limits: 16 decisions per application, 5 looks at an unchanged page.
7. **Everything runs in the seeker's browser.** The backend authenticates, stores state, provides the profile and the resume, and calls OpenAI for the decision. Every stop for the seeker is recorded (`POST items/:id/stops`, reported at `GET /extension/stops`).

Proof: `npm run test:runtime` drives the built extension in a real Chromium against local fixture pages (a one-shot form with a resume upload; a listing → 3-step dialog with a rejected value, a type-ahead, a tick list and a radio) with a stand-in AI.
